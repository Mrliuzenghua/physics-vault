## 3. 共享工作区协议

1. 先检查工作区状态。现有改动可能属于用户或其他 AI，绝不回滚、格式化或顺手清理不属于本任务的文件。
2. 一次变更只服务一个职责边界；禁止“拆分模块时顺便改产品逻辑”。
3. 修改前声明文件租约：本轮要修改哪些文件、为何修改、预计何时释放。其他 AI 不同时编辑这些文件。
4. 跨工作流的 HTTP 字段、共享 TypeScript 类型、数据库表或 MCP 契约只能由代码地图 3 修改；提出方应给出向后兼容方案和调用方列表。
5. 每次提交给集成者的结果必须包含：变更文件、保留的行为、已运行测试、未验证风险、后续建议。
6. 若同一问题同时影响两个工作流，先写最小 ADR（背景、选择、影响）到本目录，再开始实现。

## 4. 技术边界

```text
前端页面/组件 → 前端领域服务与 hooks → HTTP API 契约
                                      ↓
Router（协议校验） → Service（业务编排） → Repository / 文件存储 / MCP
```

- 前端页面不得直接管理大量 API 细节或跨页面持久状态。
- Router 只做鉴权/参数/响应协议；不得嵌入业务流程或 SQLite 查询。
- Service 编排领域规则；Repository 只处理存储；`ImportBatchStorage` 只管理导入批次文件一致性。
- 标准题库与审核库不得被重构绕开；导入结果先进入审核草稿。

## 5. 统一完成定义

一个优化任务只有同时满足以下条件才算完成：

- 职责变得更单一，且新旧模块的输入、输出和副作用写入对应分工文档。
- 外部 API、前端交互和数据边界保持兼容；若必须调整，已由 03 工作流提供迁移层。
- 新增或调整直接相关的测试，原有相关测试通过。
- 不引入循环依赖、共享“万能工具文件”或无归属的全局状态。
- `git diff --check` 通过，且变更范围内无未解释的格式化噪声。

## 6. 建议执行节奏

1. 各工作流先只提交“职责卡片 + 拆分计划”，由 00 确认无接口冲突。
2. 每流选择一个可独立验证、可回滚的小切口实现，不并行触碰公共契约。
3. 代码地图 3 集中处理必要的接口/类型迁移；代码地图 2 和 1 随后切换调用方。
4. 00 执行跨工作流测试与人工回归清单，合并文档进展。
